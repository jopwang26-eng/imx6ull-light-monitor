# 2026-11-04：AP3216C 开发前实际基线

## 原理图与板级源码

硬件连线见[公开硬件说明](../HARDWARE.md)：底板 U9 经 J2-34/35 连接 SoC I2C1，INT 另接 GPIO1_IO01。未通过本次检查证明芯片寄存器或实际响应。

通过 SSH 读取 Ubuntu 实际 imx6ull-alientek-emmc.dts：

```dts
&i2c1 {
    clock-frequency = <100000>;
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_i2c1>;
    status = "okay";

    /* 同一控制器下还存在 mag3110@0e 等既有配置。 */
    ap3216c@1e {
        compatible = "ap3216c";
        reg = <0x1e>;
    };
};
```

imx6ul.dtsi 第27/28行的实际别名为 i2c0=&i2c1、i2c1=&i2c2，因此该控制器在当前 DTS 预期对应 Linux 总线0，设备标识为0-001e；仍需板端 sysfs 确认运行时实例。

对 /var/lib/tftpboot/imx6ull-alientek-emmc-lightkey-test.dtb 使用实际 BSP dtc 反编译，已确认部署文件也包含 compatible="ap3216c"、reg=<0x1e>，不是只据源码猜测。

## 已有驱动线索

实际内核树存在 drivers/char/ap3216c.c、ap3216c.o、.ap3216c.o.cmd；实际 .config 第1620行为 CONFIG_LITEON_AP3216C=y。这说明 BSP 配置和构建树存在内置驱动，不能据此宣称用户已完成本项目传感器驱动或芯片实际读取成功。

下一步从板端读取 /sys/bus/i2c/devices/0-001e/name、driver 链接及 /dev/ap3216c，确认当前绑定。未修改设备树、解绑既有设备或访问传感器寄存器。新驱动由用户从零编写，必须先处理实际资源占用。

## 板端绑定原始输出

```text
/ # cat /sys/bus/i2c/devices/0-001e/name
ap3216c
/ # ls -l /sys/bus/i2c/devices/0-001e/driver
lrwxrwxrwx    1 0        0                0 Jan  1 05:38 /sys/bus/i2c/devices/0-001e/driver -> ../../../../../../../bus/i2c/drivers/ap3216c
/ # ls -l /dev/ap3216c
crw-rw----    1 0        0          10,  62 Jan  1 00:00 /dev/ap3216c
```

已确认运行时 client 为0-001e且由内置ap3216c驱动绑定，旧字符设备10:62已存在；不能重复让另一驱动同时绑定。

实际读取 drivers/char/ap3216c.c 第275-297行：probe 初始化芯片并注册 misc，remove 只注销 misc。其 OF 表为 LiteOn,ap3216c，与当前裸 ap3216c 不同，另有 ap3216c 传统ID匹配；新驱动将独立命名 lightap3216c，沿用当前 compatible 和 ID，通过临时 unbind 释放client后再加载。不修改当前 DTB，也不关闭共享I2C控制器。

当前 BSP include/linux/i2c.h 第170/171行确认 probe(client,id)、int remove(client) 的签名。此基线检查时新模块尚未编写、编译和上板，不能据本段记录接管成功。早期最小参考副本未纳入公开仓库，当前已验收实现见[正式驱动](../../drivers/lightap3216c/lightap3216c.c)，后续结论见[验证汇总](../VALIDATION.md)。
